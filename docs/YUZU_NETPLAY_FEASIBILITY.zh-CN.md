# yuzu 房间客户端兼容：可行性与实施方案

评估日期：2026-11-05。评估对象：仓库根目录的主运行时，入口为 runtime/hle_net.c 与 runtime/net_relay.c。本文记录方案评估与实施进度。已实现 Windows 实验性连接端、客户端启动入口及自动测试。2026-11-05，用户在 UDP 枚举修复后报告：与 Eden（此前确认为 0.2.0）及另一个未具名的 yuzu 兼容客户端进行了多场完整对局，均可用。使用方式见 YUZU_CLIENT.md。

## 1. 建议与结论

用户已收紧范围：只实现 OpenSmash 的连接端，使其能够连接现有 yuzu 兼容房间服务器，并与房间内采用兼容协议的其他客户端游玩；不开发、移植、打包或部署房间服务器。

建议增加可选择的 yuzu 兼容客户端后端，保留现有 OpenSmash 联机。首版目标是：OpenSmash 加入现有兼容服务器，与一个已固定版本的参考客户端，使用 Smash 13.0.5 的 Local Wireless 模式互相创建、加入游戏内房间，并完整打完比赛。之后按协议与实测结果扩展客户端兼容矩阵。

可行性判断：

| 目标 | 判断 | 成功标准 |
| --- | --- | --- |
| OpenSmash 连接现有 yuzu 兼容房间服务器 | 高 | 握手、昵称、密码、虚拟地址、成员信息与消息收发正确 |
| OpenSmash 与兼容协议的参考客户端混合联机 | 中等偏高，值得做原型 | 双向创建和加入游戏内房间、比赛、结算、再开一局 |
| 扩展到其他支持 yuzu 房间的客户端 | 按协议适配与实测确认 | 同协议可复用实现，有差异的版本独立记录并验收 |
| 混合对局使用 OpenSmash 的回滚同步 | 首版不做 | 远端也必须实现相同回滚协议及一致的状态恢复语义 |

表中的“中等偏高”记录实施前基于源码结构的判断。后续用户实测已确认：修复 UDP 枚举差异后，与 Eden 及另一个 yuzu 兼容客户端的多场完整对局可用，混合对局的核心目标已在这些受测组合上得到验证。其他客户端和运行条件继续按实测结果记录。

如果目的只是改善现有 OpenSmash 玩家间的延迟和稳定性，移植的收益目前没有证据支持；如果目的是与模拟器玩家互联，移植才有明确价值。

### 本次明确的范围

包含：客户端配置与连接、握手和错误提示、房间成员及虚拟地址、LDN 游戏房间操作、游戏 UDP 代理、退出和断线清理、重连后的会话隔离、客户端日志与兼容测试。

不包含：房间服务器实现或移植、服务器内置托管、独立服务打包、部署脚本、服务端公共目录、服务端账号与管理系统，以及修改现有服务器协议。服务器只作为外部兼容对象和测试依赖。

“只做连接端”不限制 OpenSmash 在游戏内担任主机：外层 yuzu 房间服务器转发网络消息，游戏内 Local Wireless 主机负责创建比赛和同步游戏房间，两者不是同一角色。若不另行收紧，首版保留游戏内创建与加入两个方向。

## 3. 两套系统的差别

“模拟器房间”是客户端先加入的网络空间；“游戏房间”是在该空间里通过 Local Wireless 创建的会话。加入前者不等于完成后者。

| 层次 | 本项目现状 | 对照源码 | 移植工作 |
| --- | --- | --- | --- |
| 外层房间 | 自有 SN 协议 v2/v3、大厅代码、模组/运行时检查 | ENet 房间，Join/RoomInformation/代理消息 | 新增房间客户端及消息编解码 |
| 游戏房间发现 | 周期 LM_ADVERTISE，通过大厅查询或广播收集 | Scan 请求、ScanResp 响应 | 调整扫描入口、等待与结果缓存 |
| 加入和成员同步 | LM_JOIN/LM_ACCEPT/LM_REJECT，自有心跳和超时 | Connect 携带 NodeInfo，SyncNetwork 同步 NetworkInfo | 转换语义并保留正确的游戏状态事件 |
| 游戏数据 | 虚拟 UDP，直接或经现有中继发送 | ProxyPacket，经 Zstd 压缩，再交给 ENet 房间转发 | 端点、枚举、大小端、压缩及回包投递 |
| 虚拟地址 | 固定 10.13.0.0/16 | 房间默认分配 192.168.x.y | 抽象网络参数，直接向游戏提供远端认识的地址 |
| 游戏结构 | NetworkInfo 0x480，NodeInfo 0x40 | 同样大小，主要字段布局可对照 | 逐项核验偏移、字节序、名字和版本，不能仅比较长度 |
| 扩展功能 | P2P、v3 配对、NEX Quickplay、回滚 | 此房间传输不提供这些 OpenSmash 扩展 | 用后端能力控制功能入口 |

### 必须处理的具体问题

1. **地址过滤会直接阻断数据。** runtime/hle_net.c 的 sendto 检查目的地址必须在 NET_SUBNET/NET_MASK 中；GetCurrentIpAddress、网络配置和广播判断也引用固定常量。只换 net_send 而不修改这些位置，会把 yuzu 地址当成不可达。
2. **不要在未知游戏载荷里做简单地址替换。** 游戏可能把地址写进应用数据。优先把房间分配的虚拟地址直接提供给游戏。按字节数组、宿主整数、客体内存和网络端点分别约定表示，统一用转换函数。
3. **端口常量不是线上的枚举。** 对照源码 Domain::INET 的值是 0，Protocol::UDP 是 2。不能把 Windows AF_INET=2、IPPROTO_UDP=17 直接写到对应字段。
4. **压缩是游戏代理载荷层的一部分。** ProxySocket::SendPacket 使用 Zstd；收包会解压。ENet 握手成功而缺少这层，会出现房间正常、对战数据无法解析。要限制解压窗口、输出长度、排队字节数，并核对截断及坏包行为。ENet 协议自身的压缩与这层 Zstd 是不同事项。
5. **心跳规则不兼容。** 本项目主机按 LM_KEEP 更新成员活跃时间，6 秒不更新会移除；yuzu 的所查 LDN 协议不发送这个自有消息。兼容后端不能沿用该超时判定，应基于房间连接和成员事件，以及经实测确认的游戏会话规则处理离线。
6. **不要把整个模拟器房间的成员视为同一游戏会话。** 对照房间上限是 254 个连接，LDN 游戏网络上限是 8 个节点。路由、断线处理和 UI 需要区分两个成员集合。
7. **可靠传输不等于低延迟。** 对照源码用 ENet channel 0 的可靠消息发送游戏代理包，服务端亦如此。丢包时的重传和排队可能增加等待；这是需要测量的风险，不能据此承诺比当前 P2P 更流畅。

## 4. 推荐架构

保留游戏调用的 nn::ldn 与 socket HLE，在其下方选择客户端后端。新增后端只作为外连客户端接入现有 yuzu 兼容房间服务器：

游戏 nn::ldn / socket
        |
HLE：客体结构、事件、虚拟 socket 队列
        |
后端接口：地址配置、游戏房间操作、数据包、状态、能力
        |--------------------------------|
现有 OpenSmash 后端                  yuzu 兼容后端
SN v2/v3、现有大厅/P2P                ENet + yuzu 房间编码
现有 LDN 线上协议                     yuzu LDN 控制消息
现有 UDP 数据路径                     Zstd + ProxyPacket

建议主要使用 C 编写兼容后端，链接 ENet 与 Zstd 的 C 库，按规格实现所需消息。这样可以适配本项目以 C 为主的构建，避免连带引入模拟器的 Core、Qt、Boost、账号和网页服务。直接裁剪原 RoomMember C++ 代码也是可选路径，但需要包一层 C ABI，并处理其 common、日志和服务依赖，预计维护面更大。

### 接口与文件范围（设计与当前落地）

| 文件或区域 | 计划修改 |
| --- | --- |
| runtime/net_backend.h、net_relay.c 的后端分流 | 后端选择、能力声明、动态地址参数、启动/关闭 |
| runtime/net_relay.c | 保留现有实现，通过接口包装，不重写已验证的数据路径 |
| runtime/net_yuzu.c | ENet 客户端生命周期、外连握手、状态、收发队列和成员信息；不实现服务器监听与转发 |
| runtime/net_yuzu_wire.c、yuzu_wire.h | 有界序列化与反序列化，明确线上的枚举和大小端 |
| runtime/hle_net.c | 客体 HLE 与线上 LDN 编码解耦；修改固定网段判断和投递入口 |
| runtime/hle_net.c 的 LDN 适配 | Scan/Connect/SyncNetwork 等控制流程，复用现有客体状态和事件，不另建第二套游戏状态 |
| runtime/hle_online.c 的既有能力判断 | 新后端不提供原大厅地址，复用现有网关判断隔离 NEX，无需修改该文件 |
| runtime/gpu_menu.c、启动器、配置 | 提供后端、服务器、端口、昵称、密码；显示支持的功能 |
| tools/cc.py 及其他平台构建脚本 | 构建并链接 ENet/Zstd，分别核对静态库、DLL 和平台依赖 |
| tools/dev 与 tests | 独立协议测试、LDN 测试和原有后端回归 |

HLE 保持一份游戏可见状态，不做两套互不一致的状态机。先把现有“游戏状态处理”和“线上消息编码/定时规则”分开，再为不同协议实现适配；不要把所有兼容分支塞进现有 net_relay.c。

网络线程把事件放入有界队列，由统一入口更新游戏状态并唤醒等待者；若沿用现有接收线程直接投递模式，必须遵循现有锁顺序，不能持锁等待游戏线程。明确谁持有 ENet host/peer，确保退出、重新连接和暂停加载期间不会访问已释放对象。

配置示例仅表达预期界面，并非当前已可使用的功能：

- 联机方式：OpenSmash / yuzu 兼容。
- yuzu 服务器：地址、端口、昵称、房间密码。
- 首版通过地址和端口直接连接现有房间服务器；密码和目标协议要求的连接字段在客户端处理。
- 公共房间目录/API 浏览，以及额外的服务认证，不属于首版；后续若确有目标服务需要，只评估客户端接入部分。
- 按协议能力判断兼容性，不只按客户端名称判断。记录参考客户端版本与测试结果；未知协议明确提示不兼容，不静默切到原有大厅。

## 5. 首版功能边界

首版支持 Windows、一个固定版本的参考兼容客户端、Smash 13.0.5、双方无模组、两人 Local Wireless，连接一台已有且可用的 yuzu 兼容房间服务器。OpenSmash 和参考客户端分别担任游戏内主机都要通过验收。服务器由测试环境或用户提供，项目不承担其建设和运维。

首版使用游戏原本的本地无线联机同步。OpenSmash 回滚在混合模式中禁用，并在启动或配置界面解释原因；远端不认识它的 HELLO/PADS 等消息。回滚开启与兼容后端冲突时应明确报错或要求选择，避免静默切换。

现有 OpenSmash v3 配对、模组哈希检查、Quickplay/NEX 和 P2P 不应在 yuzu 模式中显示为可用。兼容房间没有现有的运行时版本与模组协商字段，不能照搬这些筛选逻辑，也不能假定模拟器会做同等检查。首版通过锁定客户端与游戏版本、关闭模组控制变量；后续兼容信息优先由客户端本地清单、提示与实测矩阵管理，不要求修改房间服务器或其他客户端。

服务端工作从本方案中移除，不作为后续阶段保留。可以读取既有服务器源码来确认线上格式与转发行为，但交付物只包含客户端。集成验收使用现成服务器；客户端单元测试可使用固定消息样本与轻量测试替身，不交付新的房间服务。

## 6. 分阶段实施与验收

以下为一名熟悉本项目和 C/网络开发的工程师的客户端工作量估算，不是交付承诺；假定已有可连接的房间服务器、可运行的参考客户端、相同游戏数据及两台测试电脑。服务器开发与部署工时为零，不计入本计划。

| 阶段 | 内容 | 验收条件 | 估算 |
| --- | --- | --- | --- |
| 0：锁定基线 | 选定已有服务器与参考客户端，记录哈希、游戏版本，采集真实握手/LDN/数据包 | 获得可重复的参考客户端之间的对照场景及消息样本 | 1–2 人日 |
| 1：外层房间客户端原型 | 独立客户端连接现有房间，处理密码、版本、昵称、虚拟地址与消息 | 能与参考客户端同房；代理数据收发一致，错误可解释 | 2–4 人日 |
| 2：基础接口 | 抽象后端和地址，接入 ENet/Zstd，不改变游戏逻辑 | 原后端回归通过，兼容模式虚拟 UDP 字节一致 | 3–5 人日 |
| 3：LDN 互通 | 双向 Scan、游戏内创建/加入、成员变化、退出和超时 | 双向创建/加入游戏内房间，等待 60 秒不误掉线，能正确退出重入 | 4–7 人日 |
| 4：真实对局 | 角色选择、开局、比赛、结算、连续再战；定位协议或时序问题 | 两台电脑混合客户端连续至少 10 局及约 1 小时运行，无稳定复现的通信错误 | 5–10 人日 |
| 5：接入与回归 | UI、配置、日志、诊断、文档和兼容提示 | 朋友按说明可操作；既有 native 联机与离线不退化 | 3–5 人日 |

合计约 18–33 人日，即约 4–7 周的可交付两人客户端版本。首个“是否值得继续”的房间连接原型约 3–6 人日。上一版主体工时本来就集中在客户端互通，因此删除服务端设想不会使这部分工作量大幅降低。进一步覆盖 3/4 人、DLC、复杂家庭网络、多种客户端版本、平台构建及较完整回归，预留到总计约 6–10 周或更久；这些仍是客户端扩展工作。

阶段 1 只证明能连接外层房间，阶段 3 证明游戏内房间可用，阶段 4 才能对外称为支持混合对局。若阶段 0 无法在已有服务器上建立可重复的参考客户端之间的对照，应先解决外部测试基线，不把服务端修复纳入移植工作。

## 7. 测试重点和停止条件

自动测试应验证结果而不是重复实现：

- 已知真实样本的编码/解码、短包、错误长度、超大向量、未知消息；拆包与解压的长度上限。
- 地址与端口转换，Domain/Protocol 枚举；单播、广播、0.0.0.0 绑定与循环回送语义。
- 房间入退、LDN 加入/退出、主机销毁网络、成员断线；不发生 6 秒误踢。
- 加载和暂停期间的数据排队、重连后的旧包隔离、关闭时线程退出。
- 现有大厅、私人房、P2P、回滚的回归；后端能力开关不串用。

真实比赛按以下顺序扩大范围：同机两实例 → 两台电脑同一局域网 → 连接已有服务器的互联网对局 → 受控延迟/丢包/抖动 → 3/4 人与 DLC。两种主机方向分别测，记录双方网络日志、ENet 队列、压缩前后长度、游戏通信错误和操作延迟。

关键停止条件：

1. 目标客户端与源码基线格式不同：先修订基线，不能用“yuzu 通用协议”掩盖版本差异。
2. 无法证明真实 UDP 载荷字节一致：先排除编码、地址和 Zstd，不进入游戏逻辑修改。
3. 消息互通正确但比赛仍持续失败：对照游戏版本、模组、帧速、超时及 HLE 语义；此时工期不再按简单协议移植估算。
4. 实测延迟明显劣于现有后端：将其定位为“兼容模拟器的选择”，不替换默认后端。

## 2026-11-05：Eden 0.2.0 实测后的协议修正

用户实测确认：连接现有 yuzu 房间与双向发现游戏房间成功，但加入超时。保留的 OpenSmash 当房主日志显示，Eden 的 LDN Connect 已到达，OpenSmash 已返回 SyncNetwork，随后游戏从 UDP 12345 端口持续广播，却没有收到游戏 UDP 回应。

核对 Eden 官方 v0.2.0 标签，提交 ee188168c12188340961314e1dfc70a4f7ad4f7a：它在 Domain 和 Protocol 枚举开头新增了 Unspecified，因此 IPv4/UDP 的序列化值变为 1/3，历史 yuzu 基线则是 0/2。房间协议号仍为 1，不能依靠入房成功判断游戏 UDP 格式一致。Eden 的代理套接字会把旧格式 UDP=2 视为 TCP 并忽略。

实现改为默认使用 Eden 格式，允许通过 SSBU_YUZU_PROXY_PROFILE=yuzu（启动器 -ProxyProfile yuzu）选择历史格式；接收端只接受完整的 1/3 或 0/2 UDP 组合。一个发送操作只产生一份代理报文，没有自动协商或双份发送。此选择针对游戏对端，与房间服务端名称无关。未扩大服务端范围。

已增加独立的 Eden 报文字节用例和 LDN 加入后的游戏 UDP 回归，19 项客户端集成测试与 9 项编解码测试通过。公开参考源码的版本与哈希记录在 docs/YUZU_PROTOCOL_SOURCES.json；原始复现日志只保留在本地，不纳入源码提交。随后用户报告修复后的多场跨客户端完整对局均可用，详见下方实测记录。
